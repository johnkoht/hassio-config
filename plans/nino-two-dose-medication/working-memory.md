- **[Task 1]** Whitespace-safe multiline Jinja in a YAML `state:` template — use a **literal block scalar `|-`** (not folded `>`/`>-`) with every line (both `{% %}` control lines and bare-word/`{{ }}` output lines) at the **same indentation column**. Because the block is literal, YAML strips the common indent so every line lands at column 0 before Jinja sees it; combined with HA's `trim_blocks`/`lstrip_blocks`, control-tag-only lines vanish entirely and output lines emit with zero stray leading/trailing whitespace. Avoids the ambiguity of folded-scalar (`>`) whitespace-preservation-via-differential-indentation tricks (as used in `garage_entry_door_auto_lock.yaml:73-79`, which works only because of a specific folding boundary between same-indent and more-indented lines — don't copy that pattern for a `state:` field where exact string equality matters). See `packages/people/nino/medication_reminder/nino_daily_medication_reminder.yaml:87-110` for the applied pattern.
- **[Task 1]** Guarding `today_at()` against an invalid `input_datetime` state: gate with a boolean computed via `states(...) not in ['unknown','unavailable','','None']`, then AND that boolean into the SAME `{% set %}` line as the `today_at()` call (e.g. `{% set due = ok and now() >= today_at(t) %}`). Jinja/Python `and` short-circuits, so `today_at()` is never evaluated when `ok` is false — this is a second, redundant layer of safety on top of an outer `{% if not ok %}` guard.
- **[Task 2]** `trigger: template` inside `wait_for_trigger`, reading an automation-level `variables:` entry (`taken_boolean`), is the mechanism used for the wait's taken-trigger at `packages/people/nino/medication_reminder/nino_medication_reminder.yaml:252-254`. **UNVERIFIED — do not treat as confirmed.** The supporting evidence is a reading of HA's `async_initialize_triggers(variables=...)` call path, which is reasoning, not observation. A YAML parse proves nothing whatsoever about trigger variable scoping; do not cite it as support. No precedent for this pattern existed in this repo before this task. **Post-merge criterion 7 (ZHA button during an open wait) is the first real test.** Until it passes, the snooze guard at `:212` and `:289` is what keeps a silent failure of this mechanism down to a spurious snooze — see the REJECTED CLAIM entry under Context Corrections.
- **[Task 2]** `trigger.id` is correct **before** `wait_for_trigger` and wrong **after** it. In the `variables:` block, `trigger.id` is the only way to know which trigger fired, so `{% if trigger.id in ['1','2'] %}` at `nino_medication_reminder.yaml:157` is right. After the wait, the fired trigger is `wait.trigger`, and reading `trigger.id` there silently compares against the automation's *original* trigger — the always-false bug at old line 166. The distinction is positional, not syntactic.

  ⚠️ **Framing correction (orchestrator).** An earlier version of this entry described rephrasing `==` to `in [...]` as a way to "satisfy a literal grep-style AC" that bans the substring `trigger.id ==`. The AC bans that substring because it is trying to catch the post-wait bug; the correct response is to be right about *where* you're reading the trigger, and let the grep pass as a consequence. - **[Task 2] `git mv` + a still-in-flight Write/Edit sequence can silently under-stage a commit.** When a file is renamed via `git mv` shortly after (or interleaved with) tool-based content edits, the index can end up holding an earlier version of the content than what's on disk — `git commit` then succeeds with a misleadingly-labeled "0 insertions/0 deletions, pure rename" diff even though the working tree has substantial changes. Caught here because AC self-checks were re-run against `git show HEAD:<path>` (the actual committed blob), not just the working-tree file, and disagreed. **Always diff the committed blob against the working tree before declaring a commit done**, especially after any `git mv` in the same task. Also: never chain a possibly-failing `git add <path-a> <path-b>` — `git add` aborts entirely (stages nothing) if any single pathspec doesn't match, silently leaving stale index state in place.
- **[Task 2] HA template variables that render numeric-looking text come back as `int`, not `str` — repo-wide trap, not specific to this file.** `Template.async_render()` (a) strips the rendered text, then (b) runs `homeassistant.helpers.template._parse_result`, which does `literal_eval(stripped)` and returns whatever Python type comes out *whenever it isn't a string*. This applies to **every** template HA evaluates as a whole unit — `condition: template` values, `variables:` entries (automation- and script-level), template sensor `state:` — not just entity-ID interpolation. Concretely, for `dose: >- {% if trigger.id in ['1','2'] %}{{ trigger.id }}{% else %}{{ states(...) }}{% endif %}`: render → `'\n  1\n'`, strip → `'1'`, `literal_eval('1')` → the **int** `1`, and since `1` is not a `str`, `_parse_result` returns the int. So `dose` is `1`/`2` (int), never `"1"`/`"2"` (str) — even though every intermediate token in the template was text. Chained templates compound this: a script `variables:` block that reads an already-int upstream variable and reassigns it (`{{ dose }}` alone, or even after `| string` *inside* the template) still gets re-parsed to int by `_parse_result` on the **final** rendered text of that variable's own template — the `| string` filter only controls what happens *inside* Jinja, not what HA does to the finished text afterward. Confirmed by porting `_parse_result` and running the actual committed templates through render → strip → parse, with `trim_blocks` both on and off — identical result in all four combinations. **Fix: coerce with `| string` at the point of comparison** (`{{ dose | string in ['1', '2'] }}`), not by trying to make the source template "return a string" — you can't, because the coercion has to survive HA's own post-render parsing, and only a filter applied at the exact comparison site does. `is_state(...)` and other built-in comparison helpers do their own type-aware coercion internally and are NOT affected. Entity-ID string interpolation (`"input_boolean.foo_{{ dose }}_taken"`) is also NOT affected — the surrounding literal text makes the full rendered string fail `literal_eval`, so `_parse_result` leaves it as a string. The trap is specifically: *bare* `{{ var }}` or `[...]`-membership / `==` templates whose ENTIRE output, after stripping, is exactly a bare int/float/bool/None literal. Applied fix: `packages/people/nino/medication_reminder/nino_medication_reminder.yaml:170` (`dose | string in ['1', '2']`) and `:403` (`resolved_dose | string in ['1', '2']`). Audit any new template comparison in this codebase against this pattern before trusting it.

Corrected by holistic review + orchestrator.]** Task 5 originally used `condition: template` inside the Lovelace `type: conditional` cards and justified it with: *"HA's built-in conditional card has supported the automation-style condition schema (including `template`) since 2024.4, per HA release notes."* **That citation is fabricated and the claim is false.** Two of its supporting details were also wrong: the directory holds **17** cards, not 15, and **8 of them use `condition: numeric_state`**, so "every existing card uses only `condition: state`" was incorrect.

  ⚠️ **THE ACTUAL RULE — the Lovelace `type: conditional` card does NOT support `condition: template`.** Verified directly against the live official docs (`https://www.home-assistant.io/dashboards/conditional/`), whose complete enumerated set is: **State, Numeric state, Screen, User, Location, Time, And, Or, Not**. Template is absent. Observed runtime failure per community reports is a visible "invalid conditions" error box, not a silent hide.

  **Lesson beyond this repo**: the original entry paired a real, correct observation ("no precedent exists here") with an invented version-and-release-notes citation to explain the gap away. When no precedent exists for something, that absence is evidence worth respecting, not a hole to fill with a plausible-sounding citation. Verify against primary sources before writing a version number into shared memory.
