# LEARNINGS — packages/holidays

- **Z-Wave re-inclusion renames plugs (2026-10-15).** Moving the front yard plugs to the ZWA-2 dropped the `_1` suffix (`switch.front_door_smart_plug_1` → `switch.front_door_smart_plug`). A multi-entity `state` condition needs *every* entity to match, so one dead ID silently blocked the Halloween automations all season. Use any-on/any-off template conditions, and check live IDs after any controller migration.
- **The front yard Hue power plugs stay out of automations.** `switch.front_yard_outdoor_front_left_hue_lights` (+ `_2`) power the Hue spots and must stay on; the spots are driven by `outdoor_lighting.yaml` and `halloween_hue_scene.yaml`, which applies the HA scene `scenes/holidays/halloween_front_yard_spots.yaml`. That covers spots 11–14 as well; the Hue app's Front Yard scene doesn't.
- **Plug IDs live only in `front_yard_holiday_decorations.yaml`.** Halloween and Christmas target `switch.front_yard_holiday_decorations`; fix a rename there, nowhere else.
- **Front yard split out of `switch.christmas_lights` (2026-11-13).** The master group is trees + playroom only; the Christmas automations target `switch.front_yard_holiday_decorations` explicitly.
- **`deploy.sh --reload` doesn't reload groups or scenes.** A new `platform: group` switch needs Developer Tools → YAML → Groups, and a new scene file needs Scenes.
- **Gate `homeassistant start` triggers by time of day (2026-10-17).** An ungated startup trigger turned the decorations off at a daytime restart. Give the trigger `id: startup` and an `or: [not trigger startup, <time window>]` condition, so a restart re-applies the state the hour calls for (`halloween_lights.yaml`).
- **Christmas on-paths are gated by the season boolean, not by turning automations on/off (2026-11-13).** Enabled state lives in the registry where the repo can't see it, and removing `initial_state` doesn't re-enable a disabled automation.
- **The family room tree moved off plug 4 (2026-11-13, JK-1252).** It is now `switch.family_room_smart_plug_25`, which feeds the Christmas Trees group, the Small Tree tile and the `smart_plug_14_daily_energy` meter. Plug 4 stays in the house as the family room "North Wall Outlet" and a Zigbee router; don't repoint those. The new plug's `total_increasing` energy is a separate series from plug 4's, so the tree meter restarts from zero. A `platform: group` member change needs Developer Tools → YAML → Groups, plus a check of the tree tiles.
- **The main tree moved off plug 9 (2026-11-16).** It is now `switch.smart_plug_21_switch` (dining room bay window), which feeds the Christmas Trees group, the plugs-off automation, the Main Tree tile, the Big Xmas Tree energy card and the `smart_plug_9_daily_energy` meter. Plug 9 stays in the house as the dining room "East Wall Outlet" and a Zigbee router; don't repoint those. Plug 21's power sensor is `sensor.smart_plug_21_power`, not `_active_power`. The tree meter restarts from zero.
- **Trees and playroom plugs go off whenever the house is down (2026-11-15).** `christmas_plugs_off_when_not_home` turns off `switch.christmas_trees` and `switch.christmas_playroom_lights` on Bedtime, Away or unoccupied, with a 3-minute retry, and again when a plug is switched on by hand while the house is down (held a minute). It is deliberately not gated on the season or `christmas_active`; `christmas_not_activated` only runs while Christmas mode is on. It leaves the front yard alone. It triggers on the six member plugs, so a plug swap in `christmas_lights_group.yaml` needs the same swap there (a test checks). `playroom_lights_off` is disabled and only turns off, so it doesn't fight this.
